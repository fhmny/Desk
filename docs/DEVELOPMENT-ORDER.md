# Development Order — تطوير ونشر مكتب فهمني الإبداعي من الألف إلى الياء

**الإصدار:** 2026-11-25 · **نطاق العمل:** `desk/` فقط. هذا مشروع مستقل عن `client/` و`server/` و`Fhmny_Attendance/`.

## خريطة التنفيذ بالترتيب

الترتيب العملي للمشروع: تثبيت قواعد الخدمة ← تجهيز بيئة مستقلة ← تطوير قاعدة البيانات والـAPI ← تطوير الصفحة العامة ولوحات الأدوار ← اختبار سيناريو كامل بالديمو ← تجهيز حزمة إنتاج بلا بيانات وهمية ← إنشاء DNS وقاعدة البيانات ومشروع Python ← تشغيل واختبار حي ← نسخ احتياطي وتشغيل يومي. الأقسام التالية تفصّل خطوات النشر، ثم قسم **14** يسجل ترتيب التطوير والإضافات التالية.

## 0. القرار النهائي قبل الضغط على أي زر

- **النطاق المقترح:** `desk.fhmny.site`. لا تغيّر دومين المنصة `fhmny.site` أو Laravel الموجود.
- **الاستضافة المقترحة:** مشروع Python جديد في aaPanel على السيرفر الحالي، يُشغّل FastAPI ويقدم ملفات الواجهة الثابتة من نفس النطاق. إذا كان السيرفر الحالي لا يسمح بمشروع Python جديد، استخدم VPS منفصلًا بنفس الخطوات، ووجّه سجل DNS إليه.
- **قاعدة البيانات:** PostgreSQL جديدة باسم `desk_db` ومستخدم مستقل `desk_app`. لا تستخدم قاعدة فهمني أو تطبيق التحضير.
- **الوسائط:** روابط HTTPS فقط. صور وفيديوهات المدرسين تظل على Google Drive؛ لا رفع للسيرفر.
- **الدعم:** واتساب `01553902490`، ورابط الزر `https://wa.me/201553902490`.
- **مهم:** مسارات `/www/wwwroot/backend.fhmny.site` و`/www/wwwroot/fhmny.site` تخص مشاريع أخرى. **لا تستخرج ZIP الـDesk فوق أي واحد منها.** مسار مشروع الـDesk يجب قراءته من aaPanel بعد إنشائه، ثم استخدامه في الأوامر أدناه بدل `<DESK_ROOT>`.

## 1. جهّز المعلومات قبل النشر

سجّل عندك، خارج Git، القيم الآتية:

| القيمة | أين تجدها |
|---|---|
| `<SERVER_IP>` | عنوان السيرفر الذي ستشغّل عليه الـDesk. |
| `<DESK_ROOT>` | المسار المطلق الذي تعرضه aaPanel لمشروع Python الجديد. مثال **غير مؤكد**: `/www/wwwroot/desk.fhmny.site`. |
| `<PG_PORT>` | نفّذ `SHOW port;` على PostgreSQL الفعلية. لا تفترض 5432 أو 5433 من مستندات قديمة. |
| كلمة مرور `desk_app` | أنشئها عشوائيًا واحفظها في مدير أسرار. |
| `DESK_SETUP_KEY` | مفتاح عشوائي طويل لإنشاء أول أدمن مرة واحدة، ثم يُحذف من البيئة. |
| بريد وكلمة مرور أول أدمن | بيانات جديدة حقيقية؛ لا تستخدم حسابات الديمو. |

## 2. تأكد من حزمة الإصدار المحلية

من جهاز التطوير داخل `desk/`:

```powershell
cd backend
py -3 -m pytest -q
cd ..\frontend
py -3 build_static.py
cd ..
py -3 scripts\package_release.py
```

الناتج `desk/release/desk-release.zip` وملف `manifest.json` و`SHA256SUMS.txt`. راجع الهاش قبل الرفع وبعده. الحزمة لا تحتوي على `.env` أو قاعدة الديمو أو حساباته أو ملفات `client/server`.

إذا كان `frontend/dist` موجودًا بالفعل، `build_static.py` يرفض الكتابة عليه. انقل النسخة القديمة لمجلد آخر داخل مساحة العمل قبل إعادة البناء؛ لا تحذف بناءً عشوائيًا. الواجهة الثابتة هنا تعمل دون npm، وتستخدم API من نفس النطاق. ملفات React موجودة للتطوير اللاحق، لكنها ليست ملف النشر الحالي.

## 3. أنشئ النطاق الفرعي في DNS

في مزوّد DNS الذي يدير `fhmny.site` (قد يكون Cloudflare أو لوحة شركة الدومين):

1. أضف سجل `A`: الاسم `desk`، والقيمة `<SERVER_IP>`.
2. لو تستخدم Cloudflare، اجعله **DNS only** أولًا حتى يصدر aaPanel شهادة SSL مباشرة؛ يمكن مراجعة وضع البروكسي بعد نجاح HTTPS.
3. انتظر انتشار السجل، ثم افحص `nslookup desk.fhmny.site` من جهازك؛ يجب أن يظهر `<SERVER_IP>`.
4. لا تغيّر سجلات `@` أو `www` أو `backend` الخاصة بالمنصة.

## 4. أنشئ قاعدة بيانات الـDesk منفصلة

على السيرفر، افتح Terminal/SSH بصلاحية إدارة PostgreSQL. أولًا افحص النسخة والمنفذ الفعلي:

```bash
sudo -u postgres psql -c 'SHOW port;'
sudo -u postgres psql -c 'SELECT version();'
```

أنشئ مستخدمًا وقاعدة مستقلين. أدخل كلمة المرور تفاعليًا عبر `\password` كي لا تظهر في تاريخ أوامر الشِل:

```bash
sudo -u postgres psql
CREATE ROLE desk_app LOGIN;
\password desk_app
CREATE DATABASE desk_db OWNER desk_app;
\q
```

إذا كان PostgreSQL في خدمة/حاوية مختلفة، طبّق الخطوات نفسها على تلك الخدمة مستخدمًا عنوانها ومنفذها الحقيقيين. لا تنشئ جداول الـDesk في قاعدة منصة فهمني.

## 5. أنشئ مشروع Python مستقل في aaPanel

1. من aaPanel: **Website → Python Project → Add Project**.
2. اختر Python 3.11 أو 3.12، وبيئة افتراضية مخصصة باسم واضح مثل `desk-env`.
3. حدّد مشروعًا جديدًا للـDesk، ثم انسخ المسار الفعلي المعروض في aaPanel إلى `<DESK_ROOT>`. لا تستخدم مسار PHP الموجود.
4. ارفع `desk-release.zip` إلى `<DESK_ROOT>` واستخرجه **هناك فقط**. يجب أن تصبح المسارات: `<DESK_ROOT>/backend/app/main.py` و`<DESK_ROOT>/frontend/dist/index.html`.
5. داخل بيئة المشروع الافتراضية شغّل `pip install -r <DESK_ROOT>/backend/requirements.txt`.
6. أمر التشغيل للمشروع (من `<DESK_ROOT>/backend`):

```text
uvicorn app.main:app --host 127.0.0.1 --port 8017 --proxy-headers --forwarded-allow-ips 127.0.0.1
```

المنفذ `8017` مثال اختياري؛ استخدم منفذًا محليًا غير مستخدم وسجّل الرقم الفعلي. لا تفتح منفذ Python للعامة في جدار الحماية؛ aaPanel/Nginx سيصل إليه محليًا فقط.

## 6. ضع ملف البيئة السري على السيرفر

أنشئ `<DESK_ROOT>/backend/.env` **يدويًا على السيرفر فقط**. لا تضفه إلى ZIP أو Git:

```dotenv
DESK_ENV=production
DESK_DATABASE_URL=postgresql+psycopg://desk_app:<URL_ENCODED_DB_PASSWORD>@127.0.0.1:<PG_PORT>/desk_db
DESK_STATIC_DIR=<DESK_ROOT>/frontend/dist
DESK_CORS_ORIGINS=
DESK_SETUP_KEY=<LONG_RANDOM_ONE_TIME_KEY>
```

إذا احتوت كلمة مرور قاعدة البيانات رموزًا مثل `@` أو `:` أو `/`، يجب ترميزها في URL. اختبر الاتصال قبل التشغيل. اضبط صلاحيات الملف مثل `chmod 600 <DESK_ROOT>/backend/.env` ومالك الملف على مستخدم خدمة Python. `DESK_ENV=production` يمنع التشغيل بقاعدة SQLite. لا تنسخ ملف ديمو أو مستخدمي الديمو للإنتاج.

## 7. أنشئ الجداول أول مرة فقط

من بيئة Python الخاصة بالمشروع ومن `<DESK_ROOT>/backend`:

```bash
python init_db.py
```

السكربت يرفض قاعدة تحتوي جداول بالفعل. لا تنفذ هذا الأمر في كل Deploy. التطبيق لا ينشئ جداول تلقائيًا في وضع الإنتاج. أي تغيير schema مستقبلي يحتاج migration مراجَعة ونسخة احتياطية قبل تطبيقه.

## 8. اربط النطاق وشهادة SSL في aaPanel

1. في **Python Project → Mapping**، اربط `desk.fhmny.site` بالمنفذ المحلي لمشروع الـDesk. aaPanel يضع Reverse Proxy للخدمة.
2. من إعدادات المشروع/الدومين فعّل **SSL** واستخرج شهادة للمجال `desk.fhmny.site` بعد أن يصبح سجل DNS صحيحًا.
3. فعّل التحويل إلى HTTPS بعد التأكد أن الشهادة تعمل. افحص أن `https://desk.fhmny.site/health` يعيد `{"ok":true}`.
4. افحص `https://desk.fhmny.site/`؛ يجب أن تظهر الصفحة العامة. وافحص `https://desk.fhmny.site/login.html`؛ يجب أن تظهر صفحة الدخول **بدون** أزرار حسابات الديمو.
5. افحص `https://desk.fhmny.site/api/v1/desk/public/packages`؛ يجب أن يبدأ بقائمة فارغة `[]` في قاعدة جديدة.

لو إعداد aaPanel عندك مختلف عن أسماء القوائم أعلاه، المبدأ هو مشروع Python جديد + Mapping للنطاق + SSL. وثائق aaPanel الرسمية: [Python Project](https://www.aapanel.com/docs/Function/python.html)، [Website Basics](https://www.aapanel.com/docs/Function/Website.html).

## 9. أنشئ أول أدمن ثم أغلق الإعداد

أرسل طلب إنشاء الأدمن مرة واحدة عبر HTTPS، بنفس قيمة `DESK_SETUP_KEY` الموجودة مؤقتًا في `.env`. مثال من جهازك؛ استبدل القيم قبل التنفيذ:

```bash
curl -X POST 'https://desk.fhmny.site/api/v1/desk/setup' \
  -H 'Content-Type: application/json' \
  -H 'X-Setup-Key: <LONG_RANDOM_ONE_TIME_KEY>' \
  --data '{"name":"<ADMIN_NAME>","email":"<ADMIN_EMAIL>","password":"<STRONG_PASSWORD>","role":"admin"}'
```

بعد نجاح الطلب: احذف سطر `DESK_SETUP_KEY` من `.env`، وأعد تشغيل مشروع Python من aaPanel. عندها يصبح endpoint الإعداد مغلقًا. لا تستخدم `كلمة مرور الديمو` أو بريد `@desk.demo`.

## 10. املأ الصفحة العامة وابدأ تشغيل المكتب

1. افتح `/login.html` وادخل كأدمن.
2. من **الصفحة العامة والباقات** أضف الباقات الحقيقية: السعر بالجنيه، عدد الصور والفيديوهات، عدد التعديلات، ومدة التسليم. لا تنشر أسعار الديمو تلقائيًا؛ قاعدة الإنتاج تبدأ فارغة.
3. أضف صفحة مدرس عامة ونماذج شغل فقط بموافقته ومع روابط صالحة؛ فعّل زر النشر لكل عنصر تريد ظهوره.
4. أضف حسابات المصممين والمدرسين في **المدرسون والمصممون**، وحدد المصمم ورصيد كل مدرس وفق باقته المتفق عليها. الدفع وتفعيل الباقة يدويان في هذا الإصدار؛ لا تدّع أن زر واتساب دفع آلي.
5. المدرس يرسل طلبًا، المصمم يقبله ويتحدث معه، ثم يضع رابط Drive نهائيًا ويضغط «تم التسليم». الرصيد يتحول إلى مكتمل وقتها. الأدمن يرى كل الحالات.

## 11. اختبار القبول بعد النشر

- الصفحة العامة والباقات تظهر لأي زائر دون دخول، بينما صفحة إدارة النشر ترد 401/403 بدون أدمن.
- زر كل باقة يفتح واتساب الرقم `01553902490` برسالة تتضمن اسم الباقة.
- مدرس A لا يرى طلبات مدرس B، ومصمم A لا يرى طلبات مصمم B.
- عند إسناد المدرس لمصمم آخر، يفقد القديم الوصول لكل طلبات المدرس وينتقل التاريخ للجديد.
- صورة وفيديو لهما رصيد منفصل، والتسليم يحسب مرة واحدة؛ تعديل نفس الطلب لا يخصم مرة ثانية.
- رابط المرجع يقبل HTTPS، ورابط تسليم المصمم يجب أن يكون Google Drive؛ لا توجد واجهة رفع ملفات.
- `https://desk.fhmny.site/` و`/login.html` و`/health` والـAPI كلها تفتح من نفس النطاق HTTPS.
- من متصفح الجوال، راجع الصفحة العامة والطلب والمحادثة وتبويب الأدمن. راجع سجلات Python Project في aaPanel لأي أخطاء.

## 12. النسخ الاحتياطي والتحديث والرجوع

- فعّل نسخة احتياطية يومية **لقاعدة `desk_db` فقط** باستخدام `pg_dump -Fc` إلى مكان خارج docroot، واحتفظ بنسخة خارج السيرفر. اختبر استرجاع نسخة على قاعدة اختبار منفصلة قبل الاعتماد عليها.
- قبل أي تحديث: نسخة من قاعدة `desk_db` ونسخة من فولدر الإصدار الحالي. تحقق من SHA-256 للحزمة الجديدة، ثم حدّث ملفات الكود والواجهة فقط دون استبدال `.env` أو بيانات الإنتاج.
- احتفظ بالنسخة السابقة لتستطيع إرجاع ملفات التطبيق وإعادة تشغيل Python Project. **لا ترجع schema أو الداتا عشوائيًا**؛ أي رجوع قاعدة بيانات قرار منفصل بعد مراجعة ما كُتب بعد النسخة الاحتياطية.
- إذا فشل أول نشر، عطّل Mapping الخاص بـ`desk.fhmny.site` فقط. لا تمس مواقع `fhmny.site` أو `backend.fhmny.site`.

## 13. أشياء لا تعمل تلقائيًا في هذا الإصدار

- لا تكامل دخول مع حسابات منصة فهمني، ولا دفع إلكتروني، ولا رفع مباشر إلى Google Drive.
- لا يُنشئ النشر حسابات أو باقات أو أسعارًا تلقائيًا. حسابات وباقات الديمو **محلية فقط**.
- مهارة ZIP الخاصة بالمنصة تستهدف `client` وLaravel؛ حزمة الـDesk مستقلة، وتلتزم بنفس قواعد عدم شحن الأسرار وقواعد التحقق من الجذر والهاش. مسارات الإنتاج المذكورة في مرجع المهارة سياق قديم وليست إثباتًا لجذر مشروع الـDesk الجديد.

## 14. Development order — ترتيب بناء المنتج من أول يوم

هذه قائمة تنفيذ ومراجعة للمطور القادم، حتى لو تغيّر الفريق أو انتقل العمل من الواجهة الثابتة إلى React. لا تبدأ مرحلة تعتمد على سابقتها قبل تحقق «شرط الخروج» المذكور.

### ترتيب التطوير بعد أول نشر

1. **إدارة الأسعار والباقات من الواجهة بالكامل:** تعديل الباقة ونشرها وإيقافها مع سجل يوضح من غيّر السعر ومتى؛ لا تغيّر رصيد مدرس قائم تلقائيًا عند تعديل باقة عامة.
2. **تحسين أمان وتشغيل الحسابات:** واجهة لتغيير كلمة المرور وإعادة ضبطها بواسطة الأدمن، انتهاء الجلسات، ورسائل واضحة لحالات الحساب المعطل.
3. **إشعارات فعلية:** عند طلب جديد، سؤال من المصمم، تسليم، أو طلب تعديل. ابدأ بإشعارات داخل التطبيق ثم قرر واتساب/بريد بعد قياس الحاجة والتكلفة والموافقة اللازمة.
4. **تقارير تشغيلية:** المتأخرات حسب المصمم، متوسط زمن التسليم، عدد التعديلات، الرصيد المتبقي، ونسبة عودة المدرسين. عرّف وقت البداية والنهاية لكل مقياس قبل بناء الرسم البياني.
5. **تكامل المنصة عند الحاجة:** رابط دخول واضح من المنصة إلى الـDesk، ثم ادرس SSO فقط بعد تثبيت سياسة الهوية والأدوار بين المشروعين. لا تشارك قاعدة البيانات أو ملفات Laravel مباشرة.
6. **الدفع أو رفع Drive مباشر:** مشروع مستقل بقرار تجاري وتقني لاحق؛ حالياً التسعير ظاهر والتحويل للدعم عبر واتساب، والتسليم رابط Drive.

### مراجعة أي تغيير قبل دمجه أو نشره

اكتب المتطلب في `docs/DECISIONS.ar.md` إذا غيّر قاعدة تشغيل. غيّر API والواجهة معًا، وأضف اختبارًا عندما يمس الصلاحيات أو الرصيد أو حالة الطلب. شغّل اختبارات `backend/tests/`، وافحص الواجهة على الجوال، ثم ابنِ ZIP جديدًا وراجع محتوياته والهاش. بعد النشر جرّب حسابات الأدوار الثلاثة على الموقع الحي، ثم حدّث `docs/IMPLEMENTATION_STATUS.ar.md` بنتيجة التنفيذ وأي حدود باقية.
